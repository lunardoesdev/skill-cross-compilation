# m4

GNU m4 — a *host tool* (used by autoconf and by `autoreconf` in recipes that must
generate a configure).

- build system: **autoconf** (`m4/generic.toml:2`).
- source: `ftp.gnu.org/gnu/m4/m4-1.4.20.tar.gz`, `--strip-components=1`
  (`m4/source.toml`).
- deps: none.
- recipe: `generic.toml` only.

## Overridden fields

```toml
make = false
install = false
post = """
make -j"$CORES" -C lib
make -j"$CORES" -C src
make -j"$CORES" .version
make -j"$CORES" -C doc version.texi
touch doc/m4.1 doc/m4.info*
make -j"$CORES"
make install
"""
```
(`m4/generic.toml:3-14`)

- `make = false` / `install = false`: the driver adds no steps; the `post` builds in the
  right order and installs (`m4/generic.toml:3-4`).
- The shipped man page and info manual are kept by `touch`ing `doc/m4.1` and
  `doc/m4.info*`: regenerating them would **execute the Android `m4` binary on the build
  host** (`m4/generic.toml:10-12`) — the same pattern gmp and help2man use.

## Known traps

| symptom in the log | cause | fix |
| --- | --- | --- |
| the build tries to run the freshly built `m4` on the host | doc regeneration uses the just-built binary (`m4/generic.toml:10-12`) | `touch doc/m4.1 doc/m4.info*` before the final `make` so it is not rebuilt |
| the next node's steps skipped in silence | m4 sets `make=false/install=false`, which the next node inherits (`m4/generic.toml:3-4`) | following recipes must assert `make/install` and clear args |
